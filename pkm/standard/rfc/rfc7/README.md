# RFC 7 — Host-IMP Interface（主机-IMP 接口）· Gerard Deloche

> **一句话定位**：这是**主机侧操作系统内核**的设计文档——Deloche（UCLA 的法国研究员）写的 HOST-IMP 接口软件方案。别的 RFC 在讨论"协议说什么"，这篇在讨论"内核里那两段驱动代码怎么写"。而且它的原稿是**手写的，部分字迹无法辨认**。
>
> 📄 原文见 [rfc7.txt](./rfc7.txt) ｜ 中英对照见 [zh.md](./zh.md)

## 〇、背景：一份手写稿和它的重建

1969 年 5 月，ARPANET 四站里唯一没交出"接口软件设计"的是 UCLA（Sigma 7 的接法最难，其他站都用的相对简单的机器）。这份作业落在了 **Gerard Deloche** 身上——RFC 1 里 Crocker 提过的"独立工作的 Deloche"。

最传奇的是文档的命运：

> 【RFC Editor 注】RFC 7 的原稿是**手写的**，只有部分无法辨认的副本存世。后来由 SRI 的扩展研究中心（ARC）用 NLS 系统重新录入。以下是我们能做到的最佳重建版本。

所以 RFC 7 里有好几处 **...(unreadable)（无法辨认）**。**手写 → 打字机重录 → 半世纪后数字归档**，一份 1969 年的内核设计就这样传到了你手上。

## 一、内容细读

### 1. 总体架构：两个程序（图 1）

```
  用户程序               NETWORK 程序          HANDLER 程序      硬件接口         IMP
    o---|             +-----------+      +-----------+      +------+------+
    o---| (多路复用) → |  Output   | →    |  Output   |  →   |              | → IMP
        |             |           |      |           |      |   HARDWARE   |
    o---| (分发)    ← |  Input    | ←    |  Input    |  ←   |  Interface   | ← IMP
        |             +-----------+      +-----------+      +------+------+
                          ▲                   ▲
                          └────── 缓冲池 + 接口表 ──────┘
```

**Network 程序**（网络程序）：承载用户的传输请求——多路复用、构建消息头、分包、转码、填缓冲。
**Handler 程序**（处理器程序）：驱动通道硬件——发起发送、数据链式传输（data chaining）、处理中断。

这两个程序就是今天网卡驱动 + 协议栈的 1969 版分工：**上层管"发什么"，下层管"怎么把比特送出去"。**

关键设计点：
- 通信是**全双工**的，两个程序各自再拆成"输出半部 + 输入半部"（图里只画了输出半部）
- 两个程序之间通过**缓冲池**交换数据、通过**接口表**交换逻辑信息——生产者/消费者模型的完美实现

### 2. Network 程序：多路复用 + 消息组装（II-1）

**多路复用**：把所有用户的请求堆起来，把缓冲池填满，让 Handler 一直有活干（keep the handler busy emitting）。多路复用/分发**基于链路号**（Link = 两个用户之间的逻辑连接）。

**输出消息处理**（II-1-2）：用户程序要发文本时，说明三件事：**文本位置、文本长度（字节）、目的地**。Network 程序拿到后：

```
① 构建 16 位 HOST 头：1 位追踪 + 2 位备用 + 8 位链路号 + 5 位目的主机
② 在头部和正文之间插入 16 位标记（1 + 15 个 0），让正文从字边界开始
③ 检查文本长度：超过 1006 字节就拆成多条消息
   （1006 = (8080 - 32) / 8，即最大消息 8080 位 - 头部 32 位，再除以 8 位/字节）
④ 把 EBCDIC 字符转码成 ASCII
⑤ 把消息内容填入缓冲池
⑥ 更新接口表、移动填充指针
```

注意②：**"在头部和正文之间塞 16 位填充，让正文对齐字边界"**——这是 1969 年的"内存对齐"技巧，为了让主机（Sigma 7）处理消息时不用跨字读取。今天的 struct 对齐、JSON 字段序设计，干的是同一件事。

### 3. Handler 程序：短小精悍的内核驱动（II-2）

> 这个程序会**非常短**。它将用**主模式（特权指令）**编写，并应集成到操作系统的 I/O 监控程序（supervisor）中。

- 由 Network 程序或 I/O 中断唤醒
- 控制通道硬件：发起发送、在缓冲间做**数据链式传输**（data chaining）、收到中断时测试各种设备状态
- 清空 Network 程序填好的缓冲
- 探查并更新接口表

"非常短 + 特权模式 + 并入 I/O supervisor"——这就是今天的**内核态网卡驱动**的完整定义：短、特权、中断驱动、负责数据搬运不负责业务逻辑。

### 4. 缓冲池与接口表：生产者-消费者（II-3）

- **缓冲**：每块 256 字（1024 字节），刚好装下最大消息（正文 1006 + 头与标记 4 = 1010 字节）。缓冲数量决定链路的利用率。
- **接口表**：**环形表（ring table）+ 两个指针**——Network 程序用"填充指针"写入，Handler 程序用"提取指针"读出：

```
           +--------------+----------+
           | Buffer addr. | nb bytes | <== 填充指针 (Filling pointer)
           +--------------+----------+
           |              |          |
           //    ...     //
           +--------------+----------+
           | Buffer addr. | nb bytes | <== 提取指针 (Extracting pointer)
           +--------------+----------+
```

**这就是教科书级的环形缓冲 + 双指针生产者-消费者队列**——1969 年 5 月，Deloche 在 UCLA 把它写进了 ARPANET 主机软件规格。今天 Linux 的 sk_buff 队列、Kafka 的分区、React 的 fiber 队列，全是它的远房后代。

### 5. 三个待解问题（III）

Deloche 诚实地列了三个问题：
1. **为什么 HOST 和 IMP 之间没有一个简单的控制规程？** 如果 HOST 发出的消息在传输中出错，BBN 规格里说错误会一路传到接收 HOST——那是不是需要 HOST-HOST 的控制规程？
2. **特殊通道硬件单元接在哪（MIOP/SIOP）？** 硬件怎么知道消息什么时候结束、好开始填充（padding）？反向：Handler 怎么知道进来的消息有多长——从上一条的内容推断，还是永远按最大长度准备接收？
3. **"Gordo"文档什么时候出？** 用于设计用户-网络程序接口（程序启动机制、参数传递……）。

第 2 个问题的两难（"按最大长度准备 vs 从内容推断长度"）——今天每一个流式解析器都在面对同样的选择。第 3 个问题里的 "Gordo" 是 UCLA Sigma 7 的操作系统，Deloche 在等操作系统的接口文档才能定用户-网络接口。**架构师依赖操作系统的文档，操作系统又依赖架构师的需求——1969 年的依赖地狱。**

## 二、🔷 本质升华

> - **「人类发明的实现」**：16 位头（1+2+8+5 的分配）、1006 字节、256 字缓冲、环形表双指针——全是 Deloche 为 Sigma 7 定的具体参数。换成 32 位头、MTU 1500、无锁队列，一样成立。
> - **「先于人类存在的规律」**：
>   ① **生产者-消费者律**：一个生产数据、一个消费数据，两者速率不同步——**唯一的正确解法就是中间放一个"缓冲 + 同步指针"**，让双方互不阻塞。这是从水坝蓄水、工厂流水线缓冲区、到 CPU 生产者和内存消费者之间 cache，再到网络协议栈，**所有异步系统共同的结构**。Deloche 的"缓冲池 + 环形接口表"是这条律在 1969 年的一次标准实现。
>   ② **内核态/用户态分离律**：Network 程序管逻辑、Handler 程序管硬件，后者"短小、特权、中断驱动"——**把"必须信任的硬件搬运代码"和"可以不信任的业务代码"分开**，是操作系统安全模型的原点。今天的 eBPF 把网络处理下沉到内核、DPDK 把数据面移出内核，本质上都是在调整这条分界线的位置——**分界线怎么画是人为的，分界线必须存在是必然的。**
>   ③ **内存对齐律**：头部和正文之间塞 16 位填充让正文对齐字边界——**硬件喜欢对齐、软件喜欢紧凑，折中方案就是"小填充 + 明确规则"**。C 语言的 struct padding、数据库的页对齐、SSD 的扇区对齐，全是同一件事。
>   ④ **文档残缺不阻碍思想传播**：手写稿 + 无法辨认 + 重建——但整份设计依然被读懂、被实现（UCLA 的 Sigma 7 后来真的连上了网）。**思想的传播不依赖载体的完美**，这本身又是一条规律。
> - **后世重现**：Network/Handler 分工 → 协议栈 vs 网卡驱动；主模式特权 → 内核态驱动；环形表双指针 → 无锁环形队列 / ring buffer（内核网络栈的经典结构）；1006 字节切片 → TCP 分段 / 分帧；字边界对齐 → struct padding；"按最大长度准备接收" → 固定大小 receive buffer；"Gordo 文档依赖" → API 依赖管理。**RFC 7 是这批文档里最"像现代操作系统教材"的一篇。**

## 三、亮点速览

1. **生产者-消费者环形缓冲**——教科书级实现出现在 1969 年的网络主机规格里。
2. **"非常短 + 特权模式 + 并入 I/O supervisor"**——内核态驱动的完整定义。
3. **1006 = (8080-32)/8 的拆包计算**——每个字节都有账可查的工程。
4. **字边界对齐的 16 位填充**——1969 年的内存对齐技巧。
5. **手写稿 + (unreadable) + 重建**——RFC 史上最"野生"的保存方式之一。
6. **"Gordo 文档什么时候出"**——最早的依赖管理吐槽。

## 四、成败与后续

- **成功的**：Network/Handler 分工模式在 UCLA 的 Sigma 7 主机上落地，成为 NCP 实现的基础；缓冲池+接口表设计被其他站点借鉴（SRI 的 NLS 主机接口文档里能看到相似结构）。
- **被超越的**：专用 16 位 HOST 头很快被 NCP 的统一消息格式取代；手写文档的悲剧在 RFC 20 之后的规范文档里不再重演（大家改用打字机 + 后续用机器排版）。
- **历史彩蛋**：RFC 7 的作者栏写着 "G. Deloche --> Prof. J. Estrin ..."——**这是"转发给"列表**：Deloche 写完把文档抄送给了 UCLA 的教授们（Estrin、Kleinrock、Bussel）和 Crocker。1969 年的"@mentions"。

# RFC 6 — Conversation with Bob Kahn（与 Bob Kahn 的谈话）· Steve Crocker

> **一句话定位**：这是一份**会议纪要**。RFC 1 发布 3 天后，Crocker 跑去波士顿见了 BB&N 的 Bob Kahn——两家公司里"写协议的人"和"造硬件的人"第一次面对面，把 IMP 的编码转换和 HOST-IMP 通信接口当面敲定。
>
> 📄 原文见 [rfc6.txt](./rfc6.txt) ｜ 中英对照见 [zh.md](./zh.md)

---

## 〇、背景：设计者与制造商的第一次对表

1969 年 4 月，网络上有两拨人：
- **NWG（协议设计者）**：UCLA/SRI/UCSB/Utah 写 HOST 软件的，负责"说什么"
- **BB&N（IMP 制造商）**：Bolt, Beranek and Newman 公司，负责"怎么传"，正在造 IMP 的硬件

两边各写各的规格，但 IMP 和 HOST 之间那根线缆上的**物理细节**（字符怎么编码、消息怎么切分、出了错怎么办）必须两边对齐。于是 Crocker 去 BB&N 找 Bob Kahn——**就是后来和 Vint Cerf 一起发明 TCP 的那位 Bob Kahn**——聊了一个下午。

这份 RFC 就是那场谈话的备忘录。**1969 年的"会议纪要"直接进标准文档库**——这就是 RFC 文化的日常。

---

## 一、内容细读

### 1. 编码转换：每台 HOST 一张表

```
BB&N 准备把 6/7/8/9 位字符码都转成 8 位 ASCII 再传输，
到达目的 IMP 后按同样的表转回来。
方案：一对一转换，每台 HOST 一张独特的转换表。
```

关键讨论点：
- Crocker 建议：用 6 位码的机器可能还想做**大小写切换（case shifting）**
- Kahn 回应：切换太频繁可能**溢出（overflow）**
- Crocker 让步：这种情况很少见，**"我们可以用溢出指示来代替保证"**——出错了给你个标记，但不保证一定能处理

这就是 1969 年的工程谈判：**设计者提需求，制造商报成本，最后拍板"能处理 99% 的情况 + 留个错误标记"**。和今天加需求时 PM 与开发的讨价还价一模一样。

### 2. HOST-IMP 通信：消息头里加了转换位

```
现在有了 5 位链路字段 + 1 位转换指示位。
还考虑加一个 2 位转换指示器（一位管发送前转换、一位管接收后转换），
这样系统就多了一个检查/控制的抓手。
```

### 3. 两张清单：控制面的消息类型（本节精华）

RFC 6 列出了 IMP 接口的控制消息清单：

**HOST → IMP 可以指定 9 件事：**
1. 追踪（Tracing）
2. 转换（Conversion）
3. 消息是给目的 IMP 还是 HOST
4. 发送 RFNM
5. HOST 开机/关机
6. 同步（Synchronization）
7. 格式错误消息
8. 主链路清除（Master Link Clear）
9. 请求状态（Status Requested）

**IMP → HOST 可以发 7 种信息：**
1. 转换（Conversion）
2. RFNM 已到（REFNM Arrived）
3. IMP 开机/关机
4. 同步
5. 被叫 HOST 无响应（Called HOST not Responding）
6. 格式错误（Format Error）
7. IMP 内状态（Status in IMP）

**这两张清单就是最早的"控制面协议消息类型定义"**——相当于你后来在 IP 协议里见到的 ICMP 消息类型清单、或者在 USB 里见到的控制请求清单的直系祖先。你数一下就会发现：**"状态查询/响应"、"通断通知"、"错误报告"、"同步"——今天所有控制协议的四梁八柱，1969 年 4 月的这份会议纪要里就都有了。**

### 4. 结尾

最后一句：Crocker 给 Kahn 总结了 NWG 笔记 1、2、3 号的内容（就是 RFC 1/2/3）——**设计者给制造商补课。**

## 二、🔷 本质升华

> - **「人类发明的实现」**：5 位链路字段、2 位转换指示器、"9 件事 + 7 种信息"的具体清单——全是 1969 年 4 月这次会谈的产物。换成 4 位链路、或把清单合并成 6 条，一样成立。
> - **「先于人类存在的规律」**：
>   ① **最小正交接口律**（你在 RFC 1 认过）：这两张清单就是"控制面的系统调用 API"——用最小的一组消息类型，覆盖所有"HOST 与 IMP 之间需要说的控制话"。9+7=16 种消息，今天 ICMP 有 40 多种类型，本质还是这 16 种的细化。
>   ② **异构互操作的前提是"每端一张转换表"**：编码转换用"每台 HOST 一张表"而不是"统一规定一种编码"——这是"共同分母律"的务实版：不强制改编码，只在边界做翻译。今天网关做协议转换、i18n 做 locale 映射、序列化做 adapter，全是这个思路。
>   ③ **工程谈判的取舍本质**："用溢出指示代替保证"——**当"完美保证"的成本远超"罕见故障"的损失时，正确决策是接受错误并用显式信号标记它，而不是死磕 100%。** 这就是所有可靠性工程里"尽力而为 + 错误码"模式的诞生瞬间。
> - **后世重现**：ICMP 消息类型（目的不可达/超时/回显应答）≈ IMP→HOST 的"被叫 HOST 无响应/格式错误"；USB 控制传输 + 状态请求 ≈ "Master Link Clear + Status Requested"；Linux netlink 的 RTM_NEWLINK/DELLINK 通知 ≈ "HOST up/down"；云服务健康检查探针 ≈ "IMP up/down + Status in IMP"。**16 条消息穿越了 57 年，至今还是控制面的骨架。**

## 三、亮点速览

1. **一份会议纪要直接当 RFC 发**——"谈话记录也是标准文档"，开放协作的极致。
2. **9+7 控制消息清单**——最早的协议控制面类型定义。
3. **"每台 HOST 一张转换表"**——边界翻译而非统一改造，务实到极致。
4. **"可以用溢出指示代替保证"**——教科书级的工程取舍谈判。
5. **Bob Kahn 亲自出镜**——TCP 之父在 IMP 阶段就在第一线对表。

## 四、成败与后续

- **即时生效的**：编码转换方案（6/7/8/9 位 → 8 位 ASCII + 每机一表）进入了 IMP 的正式规范；5 位链路字段 + 转换位的消息头设计被 RFC 7 的 16-bit HOST 头继承（1 位追踪 + 2 位备用 + 8 位链路 + 5 位目的，见 [RFC 7](../rfc7/README.md)）。
- **被取代的**：2 位转换指示器最终没有保留（后来的 NCP/TCP 都假设 8 位字节）；"每机一张转换表"在 ASCII 一统天下后自然消失。
- **历史意义**：这次会面确立了**"协议设计者 ↔ 硬件制造商面对面定接口"**的工作模式——比任何正式流程都更直接。Bob Kahn 后来成为 ARPANET 最关键的工程师之一，这次"被补课"的经历对他理解 HOST 侧需求帮助巨大。

## 五、思想传承对照表

| RFC 6 的内容 | 今天的对应物 |
|---|---|
| 每台 HOST 一张字符转换表 | 网关协议转换 / i18n locale 映射 |
| 6/7/8/9 位 → 8 位 ASCII | 统一字符集（后 ASCII 胜出、再被 UTF-8 继承） |
| 5 位链路字段 + 转换位 | IP 头字段设计 / TCP 标志位 |
| HOST→IMP 的 9 条指令 | 控制请求（USB Control Request / netlink） |
| IMP→HOST 的 7 种消息 | ICMP 消息类型 / 设备状态通知 |
| "溢出指示代替保证" | 尽力而为 + 错误码 / 优雅降级 |
| 会议纪要作为 RFC | 设计讨论记录 / ADR（架构决策记录） |

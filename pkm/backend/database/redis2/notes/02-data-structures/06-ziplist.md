# 压缩列表（Ziplist）

**来源**：《Redis设计与实现》第 7 章

---

## 概述

压缩列表是 Redis 为了节约内存而开发的，由一系列特殊编码的连续内存块组成的顺序型数据结构。一个压缩列表可以包含任意多个节点（entry），每个节点可以保存一个字节数组或一个整数值。

**应用场景**：列表键和哈希键的底层实现之一。

## 压缩列表的构成

| 组成部分 | 类型 | 说明 |
|----------|------|------|
| `zlbytes` | uint32_t | 记录整个压缩列表占用的内存字节数 |
| `zltail` | uint32_t | 记录表尾节点距离起始地址的偏移量 |
| `zllen` | uint16_t | 记录节点数量 |
| `entryX` | 不定 | 各个节点 |
| `zlend` | uint8_t | 特殊值 0xFF，标记压缩列表末端 |

## 压缩列表节点的构成

每个压缩列表节点由以下三部分组成：

### previous_entry_length

记录前一个节点的长度，用于从表尾向表头遍历（根据当前地址减去该值得到前一个节点地址）：

- 前一个节点长度 < 254 字节：占 **1 字节**
- 前一个节点长度 >= 254 字节：占 **5 字节**（第一个字节设为 0xFE，后 4 字节存长度）

### encoding

记录节点的 content 属性所保存数据的类型及长度。

### content

保存节点的值，可以是一个字节数组或一个整数值。

## 连锁更新

### 触发原因

当多个连续的节点长度在 250~253 字节之间时，它们的 previous_entry_length 都只占 1 字节。此时若在表头插入一个 >=254 字节的新节点，会导致：

1. 新节点 → 第一个旧节点的 previous_entry_length 需从 1 字节扩展为 5 字节
2. 第一个旧节点长度增加 4 字节 → 超过 254 字节
3. 第二个旧节点的 previous_entry_length 也需要扩展为 5 字节
4. ...连锁反应，直到结束

### 影响

- 最坏复杂度 O(N²)
- 实际发生概率很低（需要恰好连续多个 250~253 字节的节点）
- 即使发生，影响的节点数量通常很少

### 注意事项

尽管连锁更新的复杂度较高，但 ziplistPush 等命令的平均复杂度仅为 O(N)，可以放心使用。

## 重点回顾

| 特性 | 说明 |
|------|------|
| 数据结构 | 连续内存块组成的顺序结构 |
| 遍历方向 | 从表头向表尾（通过 encoding 跳转）；从表尾向表头（通过 previous_entry_length） |
| 连锁更新 | 特殊情况下的连续空间重分配，概率低 |
| 适用场景 | 元素数量少或元素长度小的列表/哈希键 |
